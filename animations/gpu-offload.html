When Does the GPU Pay Off?

Copy the data to the GPU, compute, copy the result back, and compare with the same work on the CPU. Measured on our cluster.

    About the measurements

    Where. One node of our cluster, fortran: an NVIDIA RTX PRO 6000 Blackwell GPU, the same GPU as julia, and two AMD EPYC 9755 processors, the same as haskell. Student jobs cannot run on fortran, but it was free when julia's GPU was busy. The GPU times come from a GPU job, the CPU times from a 4-CPU job on the same node, like the jobs of Exercise 2. Every time is the best of several runs of a program that had already run once.

    What is timed. The arrays start as ordinary NumPy arrays in the computer's RAM. Copy in is cp.asarray(a) and cp.asarray(b), compute is a @ b or a + b on the GPU, and copy out is cp.asnumpy(c). Each piece is timed on its own, and the GPU time is their sum. Timed in one go, the whole round trip comes within 14% of that sum, and within 5% for 21 of the 26 sizes.

    a + b repeated. The third view is not a separate measurement: it adds up the measured pieces for 100,000,000 numbers, as if the program kept its data on the GPU and ran the operation k times.

    What we left out. The first CuPy call in a program also starts the GPU and prepares its code (2.0 s here), once per program, so time a GPU program only after a first run. Copies from page-locked memory are faster than from ordinary NumPy arrays, and a program can copy and compute at the same time; here the steps run one after the other.

    More CPUs. A 64-CPU job on the same node multiplies two 16,000 × 16,000 matrices in float32 in 1.2 s instead of 15.9 s, still slower than the GPU's 301 ms. In float64 it wins: 3.5 s against the GPU's 5.7 s. For small matrices (250 × 250), starting 64 threads costs more than the work: 106 µs instead of 83 µs. We come back to this in Session 22. Adding two arrays uses one core whatever the job asks for.
