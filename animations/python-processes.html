    About this page

    Real runs. Mixed queue, Big data, Uneven tasks and Where Linux puts them replay real runs on haskell, in a job with 8 CPUs: every task stamped its own start and end. Each one is the median of 7 runs of the same program. Your times will differ a little.

    Data and compute. A compute task is the notebook's work(n). A data task is its download: time.sleep stands for waiting for a web server, a disk or a database. In Big data the data really moves.

    Threads. The stamps of the thread pool show when a task started and ended, not each turn with the GIL. So the page draws one block for a computing thread and one busy core, and a thread that wakes up from a wait may queue for the GIL first.

    Four equal tasks. The first tab and 4 workers, 2 cores use the program of the exercise: four tasks of 10 million loop steps, best of 3. One after the other 0.73 s. With 8 CPUs, 4 workers 0.18 s. With 4 CPUs, 2 workers 0.39 s and 4 workers 0.32 s.

    CPUs and cores. Each core of our nodes runs two hardware threads, and Linux and Slurm count each one as a CPU. Slurm gives out whole cores, so a job with 4 CPUs has 2 cores. Two hardware threads of one core run at the same time, but they share the core's units: here both workers on a core took 0.32 s for a task that takes 0.18 s alone.

    Placement. A fresh pool can start two workers on one core, and a single run can be slower. That is why the exercise keeps the best of 3. A job whose cores sit under two L3 caches is different, because repeating does not help: four tasks took 0.33 s instead of 0.18 s, and 12 long tasks 3.8 s instead of 2.2 s. On haskell an L3 cache serves 8 cores (CPUs 0-7 and 256-263, then 8-15 and 264-271, and so on); on julia it serves 16. In Where Linux puts them a task's core is where it started and where it ended.

    Big data. The files were in Linux's page cache, so they loaded in about 0.03 s; a cold disk or a busy file server takes longer. The stamps of this tab have no CPU numbers, so the page draws one worker on each core. The container's Python 3.14 starts workers with forkserver, not fork, and they inherit nothing: there, send the file name.

    What you do not see. Starting a pool of 4 processes and stopping it took 3.3 ms, and sending one small task and getting its result took 70 us. Both are too small to see at this scale.

    Tiny tasks. The two rows use the measured times per message: 4.65 s / 100,000 items and 28 ms / 100 chunks, with 4 workers. They show one stream of messages for simplicity.
