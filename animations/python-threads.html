All steps

    About this page

    The turns. When other threads wait for the GIL, Python asks the running thread to let go of it after 5 ms (sys.getswitchinterval() prints 0.005). We traced four counting threads on haskell: 44 turns, with a median of 5.0 ms. The real order is not this tidy rotation: the operating system decides which waiting thread wakes up first, and two threads can alternate for a while.

    The times. 20 ms of Python code and the waits are chosen to fit the screen. Measured on the cluster, four loops took 0.73 s one after the other and 0.71 s with 4 threads, in a job with 4 CPUs. Four waits of 1 s took 4.00 s one after the other and 1.00 s with 4 threads, on a single core.

    The CPUs. Here each thread has a CPU of its own. Linux can move threads between CPUs, and that does not change the picture: a thread that waits for the GIL or for the network uses no CPU.

    Compiled code. The GIL protects Python's own objects. NumPy and other compiled libraries let go of it inside their long loops, so threads can run those at the same time. Python 3.13 and later also come in a separate build without the GIL; our course environment is the standard build.

    The race. The wait between read and write stands for a database or a file. In the notebook it is time.sleep(0): 4 threads × 10,000 deposits gave a balance of about 10,000 instead of 40,000, and 40,000 with the lock, in 2.0 s instead of 0.46 s. Without a wait, c += 1 lost nothing in our runs, but Python does not promise that.
